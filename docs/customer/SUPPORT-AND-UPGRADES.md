# Support and upgrade policy

## Release channel

MENAXVI `0.1.0` is a private pre-alpha. There is no public availability, uptime commitment, or production support service-level agreement.

## Support scope

For approved private evaluations, support covers:

- installation and checksum verification;
- documented CLI behavior;
- reproducible defects in approved product paths;
- the reviewed campaign-message manual workflow;
- interpretation of generated local evidence.

Support does not cover quarantined imported content, customer-modified internals, unapproved adapters, autonomous publication, legal advice, or third-party model output.

A useful defect report includes the MENAXVI version, Python version, operating system, exact command, exit status, redacted output, and minimal reproduction. Never include credentials or private customer data.

## Versioning before 1.0

MENAXVI uses semantic version labels, but pre-`1.0` minor releases can change CLI or resource contracts. Patch releases should preserve documented behavior unless a security or correctness defect requires a breaking correction.

Each upgrade must include release notes that identify:

- user-visible changes;
- compatibility changes;
- security and provenance changes;
- required migration steps;
- rollback conditions;
- known limitations.

## Upgrade procedure

1. Keep the active release installed.
2. Back up the repository and generated evidence as documented in the [operations runbook](../operations/PRODUCT-RUNBOOK.md).
3. Build the new artifact from a trusted checkout.
4. Verify its SHA-256 checksum.
5. Install it in a new versioned release directory.
6. Run `--version`, `diagnose`, `validate`, and the source-checkout release gate.
7. Switch the user-local symbolic link only after review.
8. Retain the previous verified release until the rollback window closes.

Do not upgrade in place by overwriting the only executable copy.

## Rollback policy

Executable rollback selects the previous verified version through the user-local symbolic link. Repository rollback must restore into a new directory and pass validation before promotion. Evidence generated by a newer version must be retained with its producing version and must not be silently rewritten by an older version.

## Security fixes

A confirmed security issue can shorten the normal compatibility window. Affected releases may be withdrawn rather than patched when safe remediation cannot preserve behavior. Private evaluators must stop using an affected artifact when directed and verify replacement checksums before use.
